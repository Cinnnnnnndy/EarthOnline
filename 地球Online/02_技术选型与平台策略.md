## 1. 先说结论

**双原生 UI + 一份共用的引擎世界层 + 契约优先的共享层。** 具体是：

| 层 | 鸿蒙 | iOS | 共享 |
|---|---|---|---|
| UI 与平台能力 | ArkTS / ArkUI | Swift / SwiftUI | 不共享代码，共享设计规范与布局状态定义 |
| 微缩世界（3D 积木、风格化 CG 着色与后期、卡通小人、搭建模式） | 游戏引擎作为库嵌入原生页面（XComponent） | 同一引擎工程嵌入原生页面（UIView） | **共享一份世界层代码**（首选 Cocos Creator 3.x，TypeScript），外加积木库、贴图、角色模型与模板 |
| 领域核心（行程逻辑、导出版式） | ArkTS 实现 | Swift 实现 | **共享算法规格 + 黄金用例**，两边必须逐字节复现同一结果 |
| 数据与规则 | — | — | JSON Schema、世界生成规则表、积木模块契约 |
| 服务端（地图生成、AI 文案、链接解析、同步） | — | — | 一个后端，两端调同一接口 |

一句话：**UI 代码不共享，世界层代码共享，契约共享。** 鸿蒙先做，iOS 晚 4–6 周启动，等契约冻结后再照着契约做，而不是两边同时追一个移动的目标。

v0.2 把世界层从「各写一个薄 2D 渲染器」改成「一份引擎代码两端共用」，原因是带角度的 3D 视角、像素化后处理、体素积木的合并与实例化、用户搭建编辑，这四样合在一起已经超出自研 2D 渲染器的合理范围；而这恰好是游戏引擎的本行。副作用是好的：世界层这块最重的逻辑只写一遍。

理由分三条：

1. 这个产品最重的两块是 UI 体验（书、翻页、折叠屏双页）和平台整合（折叠状态、实况窗、Pencil、卡片）。恰恰是这两块跨平台框架给得最差、原生给得最好。世界层则相反：它是一块自成一体的 3D 画面，引擎嵌入原生页面的做法在鸿蒙（XComponent）和 iOS（UIView）都有官方路径。
2. 真正需要「两边一致」的东西是确定性的：同一趟旅程生成同一个世界、同一张网格、同一条路径、同一份导出。这类逻辑用规格 + 黄金用例约束，比共享一个二进制便宜得多，而且不引入第三种语言。
3. 团队小的时候，最贵的是「工具链出问题时没人能解」。双原生的工具链是两家厂商各自维护的一等公民；跨平台分支的鸿蒙侧不是。

## 2. 为什么不是一套代码

评估过的四条路：

| 路线 | 优点 | 代价 | 判断 |
|---|---|---|---|
| **A. 双原生**（ArkUI + SwiftUI） | 平台能力全覆盖；折叠屏适配走官方路径；上架审核最顺；两个工具链都是一等公民 | UI 写两遍；领域逻辑写两遍（但可用黄金用例锁住） | **采用** |
| B. Flutter（OpenHarmony 分支）+ Flame | 一套代码；Flame 做 2D 像素世界顺手 | 鸿蒙侧是社区/华为指导维护的分支，版本滞后；悬停态、折痕、实况窗都要自己写 platform channel；iPhone Duo 首发 API 要等 Flutter 跟进 | 备选，见第 11 节 |
| C. Cocos Creator 做整个 App | 鸿蒙 NEXT 官方支持（3.8.6+）、iOS 成熟 | 列表、表单、导出这类普通 UI 用游戏引擎做很痛苦；平台整合弱 | 不采用 |
| **C′. 原生壳 + Cocos Creator 世界层**（v0.2） | 世界层一份代码两端共用；3D、后处理、实例化现成；TypeScript 与 ArkTS 同源，一个人能同时看两边 | 原生与引擎之间要走桥；引擎启动与内存要管；折叠开合时引擎视图尺寸变化要处理 | **采用**，作为第 1 节表里的世界层 |
| D. ArkUI-X（一套 ArkTS 跑鸿蒙 + iOS） | 鸿蒙侧零成本 | iOS 侧不成熟，生态弱，折叠机新 API 更谈不上 | 不采用 |

另有一条「Rust 共享核心」的变体：领域核心用 Rust 写一遍，鸿蒙侧通过 napi 绑定（ohos-rs 项目），iOS 侧通过 UniFFI 出 Swift 接口；Rust 已有 `aarch64-unknown-linux-ohos` 目标（版本支持等级以当期 Rust 文档为准）。它把「写两遍」变成「写一遍 + 两层绑定」。**只有团队里已经有人能写 Rust 才值得**，否则黄金用例方案更稳。

## 3. 分层架构：什么共享、什么各写各的

```
┌───────────────────────────────────────────────────────────────┐
│  服务端（一个）                                                  │
│  AI 文案生成 · 链接/文本解析（P2） · 同步（P2） · 账号            │
└───────────────────────────┬───────────────────────────────────┘
                            │ HTTPS / JSON
┌───────────────┐           │           ┌───────────────┐
│ 鸿蒙 App       │           │           │ iOS App        │
│ ArkUI UI 层    │           │           │ SwiftUI UI 层   │
│ 引擎世界层(嵌入)│◄── 同一份 Cocos 工程 ──►│ 引擎世界层(嵌入) │
│ ArkTS 领域核心 │           │           │ Swift 领域核心   │
└───────┬───────┘           │           └───────┬───────┘
        │                   │                   │
        └───────────┬───────┴───────────┬───────┘
                    ▼                   ▼
        ┌──────────────────────────────────────┐
        │  shared/（契约，不是代码）              │
        │  spec/    JSON Schema：Trip/Day/Entry/ │
        │           WorldSpec/Diary/ExportDoc    │
        │  rules/   世界生成规则表、tile 契约      │
        │  assets/  tileset、精灵、字体、9-slice  │
        │  golden/  黄金用例：输入→期望输出        │
        │  algo/    算法规格：PRNG、布局、寻路     │
        │  mapgen/  地图生成器：OSM→网格→铺积木   │
        │  world/   世界层代码：Cocos Creator 工程 │
        └──────────────────────────────────────┘
```

**共享的判断标准**：如果两端结果不一致会被用户看出来，就必须进契约（世界长得不一样、路径不一样、导出版式不一样）。如果不一致是平台惯例（返回手势、系统分享面板、字体渲染），就各走各的。世界层因为是同一份代码，天然一致，黄金用例只需在它自己的测试里跑一遍。

## 4. 共享层的具体做法

### 4.1 数据规范 `spec/`

- 每种持久化对象一份 JSON Schema；每个文档带 `schemaVersion`。
- 两端各自实现迁移，但迁移规则写在 `spec/migrations.md` 里，谁先做谁写。
- 本地存储各用各的（鸿蒙关系型数据库 / iOS SwiftData 或 SQLite），但**导出的 JSON 必须能被对方导入**，这是 P0 就要过的测试。

### 4.2 世界生成规则表 `rules/`

- `biomes.json`：目的地 → 候选地形主题，季节修正。
- `palettes.json`：每个主题的色板。
- `tileset.json`：**tile 契约**——每个 tile 的 id、在图集里的位置、可通行性、站点类别到建筑 tile 的映射。两端渲染器都只认这份文件，不认图片文件名。
- `weather.json`：目的地气候档案。
- 设计师可以直接改这些文件，不需要碰两端代码。

### 4.3 算法规格 `algo/`

这是「不共享代码却要结果一致」的关键。

| 算法 | 规格要求 |
|---|---|
| 伪随机数 | 指定算法与参数（建议 mulberry32：32 位状态，十行代码，TS 与 Swift 都能逐位复现）；种子派生规则写死（`seed = hash(tripId)`，hash 算法指定为 FNV-1a 32 位） |
| 经纬度 → 网格 | 全部用整数定点运算（经纬度 × 10⁶ 取整），避免浮点在两端产生末位差异；归一化、避让、排序的顺序写死 |
| 寻路 | A*，四方向，启发式与平局打破规则写死（否则两端可能选到不同的等价路径） |
| 世界生成 | 输入 Trip → 输出 WorldSpec 的每一步都由规则表 + PRNG 决定，不允许读系统时间、不允许依赖遍历顺序不确定的容器 |
| 导出版式 | 页面尺寸、边距、字号、每页条目数写在规格里；两端出的 PDF 逐页对比 |

### 4.4 黄金用例 `golden/`

- 一组固定的旅程 JSON（3 天京都、5 天冲绳、跨城 7 天……），每份带期望的 `WorldSpec`、网格布局、每段路径、导出的版式数据。
- 两端 CI 各跑一遍，输出与期望逐字节比对。不一致就是 bug，哪边错改哪边。
- 新增规则或改算法：先改规格与黄金用例，再改两端实现。**规格是源，实现是派生。**

### 4.5 地图生成器 `mapgen/`

- 服务端跑的生成器：取 OpenStreetMap 数据 → 栅格化成分类网格 → 按地形主题的规则自动铺 tile → 输出 tilemap JSON。完整方案见 `03_地图生成与渲染方案.md`。
- 放在共享层的原因：分类规则、每个 biome 的自动铺 tile 规则（LDtk 导出的 JSON）、tilemap 输出格式都是两端渲染器共同依赖的契约。
- 黄金用例多一类：同一 bbox + 同一规则版本 → 同一 tilemap，逐字节一致。

### 4.6 素材流水线 `assets/`

- 纹理与 UI 像素图：源文件用 Aseprite（`.aseprite`）单一来源；脚本导出 PNG 图集 + JSON 元数据（帧、锚点、动画时长）。
- 积木库与模板：体素建模用 Goxel（开源）或 MagicaVoxel（免费）做源文件，导出 glTF 给引擎；每种砖一个模型，模板是砖的排列 JSON，不是整栋模型，这样用户才能改。
- 世界层由引擎工程直接消费这些资源，两端不再各放一份；原生 UI 用到的像素图（书页、卡片、图标）仍分别放 `resources/rawfile/` 与 asset catalog，关闭压缩与 mipmap。
- 字体：中文像素字体许可证上线前核实；两端用同一字体文件。

## 5. 鸿蒙侧实现

> 第九轮（D91 / D92）的做法：世界层不换 Cocos，仍是网页构建的那一份（`web/dist`），用 ArkWeb 的 `Web` 组件常驻装着，虚拟的 https 源（`onInterceptRequest` 从 rawfile 供应）让 ES 模块、fetch、IndexedDB 都正常；领域核心不再用 ArkTS 重写，而是经桥接 `core-call` 调同一份 TypeScript（`shared/core.ts`）；界面文字读导出的消息表 JSON；令牌、频道表、布局阈值是导出的 `gen/Shared.ets`。下表里「领域核心 ArkTS 实现」那一项因此改成「调共享核心」，其余照旧。工程在 `app/harmony/`，说明见那里的 README。

| 项目 | 选择 | 说明 |
|---|---|---|
| 语言 / 框架 | ArkTS + ArkUI（声明式） | API 版本取当期 HarmonyOS NEXT 稳定版 |
| 导航 | `Navigation` 组件，模式随断点切换（单栏 / 分栏） | 分栏模式天然对应「左页 / 右页」 |
| 断点 | 一多断点体系 sm / md / lg + 折叠状态 | 见第 7 节 |
| 本地数据 | 关系型数据库（RDB）+ 文件（图片） | Schema 对齐 `spec/` |

| 旅行中 | Live View Kit（实况窗）显示下一站；Form Kit（服务卡片）放今日行程 | P3 |
| 导出 | Canvas 离屏绘制长图；PDF 用系统 PDF 能力或自绘 | P0 长图，P1 PDF |
| 账号 / 同步 | 华为账号登录；同步走自建后端 | 同步 P2；不用只在鸿蒙生态可用的云能力做主同步，否则 iOS 侧没法对齐 |

## 7. 折叠屏工程细节

> 2026-10-08 改写（D90）。仓库主人：「要考虑到折叠屏前后的适配，还有普通直板机的适配，阔折叠的适配，三折叠的适配。」

### 7.1 一套规则，三端移植：`shared/spec/layout.ts`

两端 UI 代码都不认设备型号，只认**布局态**和**分页**。规则是一个纯函数 `layoutOf(info)`，输入只有几何：

| 输入 | 网页 | 鸿蒙 | 安卓 | iOS |
|---|---|---|---|---|
| 窗口宽高（CSS px / vp / dp / pt） | `innerWidth / innerHeight` | `window.getWindowProperties().windowRect` → `px2vp` | `WindowMetrics` → dp | `GeometryProxy.size` |
| 折痕分出的段 `segments` | `visualViewport.segments`（折叠机上的 Chromium）；拿不到时 CSS `(horizontal-viewport-segments: n)` / `(vertical-viewport-segments: 2)` 只给段数，按等分 | `display.getCurrentFoldCreaseRegion()` 的 `creaseRects`（三折叠两条） | `WindowInfoTracker.windowLayoutInfo` 里的 `FoldingFeature`（三折叠两条；`orientation` 定并排还是上下） | iOS 27.1 的 `reservedRegions`（未验证，隔离在 `DuoLayout`） |
| 折叠姿态 `posture` | 无（只能从段推） | `display.getFoldStatus()`：EXPANDED / FOLDED / HALF_FOLDED，三折叠的组合值（`…_WITH_SECOND_…`）折成 flat / closed / half | `FoldingFeature.state`：FLAT / HALF_OPENED；合上时没有 feature、窗口变小 | 无 |

输出五个布局态（产品构想 7.2 节的四个 + 三折叠的一个），加每一页的横向范围与折痕位置：

| 布局态 | 页数 | 含义 | 没有折痕信息时的估法 |
|---|---|---|---|
| `phone` | 1 | 手机竖持、折叠机展开后竖持（单页放大）、平板竖持 | 宽 < 600，或竖长（宽高比 < 0.8） |
| `outer` | 1 | 折叠机合上的外屏：和 `phone` 同一套，只是矮，抽屉半开要高一点 | 宽 < 600 且姿态 = 合上 |
| `spread` | 2 | 阔折叠 / 书式折叠展开横持、横持平板：左页内容，右页世界，折痕是书脊 | 宽 ≥ 600 且宽高比 ≥ 0.8（0.8 是为了收下 Galaxy Z Fold 那种近方形的内屏） |
| `triple` | 3 | 三折叠全开、宽桌面：左页内容，中页世界，右页弹层（站点详情、清单不再盖在世界上） | 宽 ≥ 1100 且宽高比 ≥ 1.3 |
| `hover` | 2（上下） | 半开悬停、横放桌面：上半世界，下半抽屉 / 键盘 | 姿态 = 半开 且 横着 |

折痕两侧的留白：量到真折痕时 = 折痕宽 + 16，否则 24。页的范围写进 CSS 变量（`--pane-n-x / --pane-n-w`、`--crease-n`、`--crease-gap`），网页与嵌入页的面板按页停靠；原生壳各自按同样的页停靠。世界按页让边（`set-insets` 四边：两页让左页、三页让左右两页、悬停让下半）。

状态机放在各端一个地方（网页 `web/src/shape.ts`，鸿蒙 `harmony/.../layout/LayoutState.ets`，安卓 `android/.../layout/LayoutState.kt`，iOS `ios/.../Layout/StageLayout.swift`），页面只读状态。`shared/spec/layout.golden.json` 是三端共用的用例（22 条：Pura X Max 内外屏、Mate XT 三折全开 / 两折 / 合上、Galaxy Z Fold、Pixel Fold、iPad、桌面……），改规则先改用例，四处移植都要跑过。

### 7.2 鸿蒙折叠 API 的用法

- 折叠状态：`display.getFoldStatus()` 取当前值，`display.on('foldStatusChange')` 监听开合。三折叠（Mate XT）的状态值是组合的（第一折 × 第二折），`LayoutState.ets` 把它折成 flat / half / closed 三种姿态，具体枚举以当期文档为准。
- 折痕区域：`display.getCurrentFoldCreaseRegion()` 取折痕矩形（三折叠两条）；折成 `segments` 交给同一套规则；跨页布局把书脊留白对齐到折痕矩形，tile 网格从折痕向两侧铺。
- 显示模式：`display.getFoldDisplayMode()`（FULL / MAIN / SUB / COORDINATION）只用来判断窗口在内屏还是外屏（`hasOuter`）。
- 悬停态：相关 API 自 API 14 起提供，具体以当期文档为准；P1 再做，P0 先把状态位留出来。
- 断点：内屏展开约落在 lg，外屏落在 sm；不硬编码 vp 数值，用同一套规则（阈值 600 / 1100 与网页一致）。
- 窗口尺寸变化时**不重建世界**：渲染层只重算缩放倍率与镜头，世界数据不动（嵌入页收 `set-layout` + `set-insets`）。

### 7.3 安卓折叠 API 的用法

- Jetpack WindowManager：`WindowInfoTracker.getOrCreate(activity).windowLayoutInfo(activity)` 是一个 Flow，每次开合、旋转发一次 `WindowLayoutInfo`；取其中的 `FoldingFeature`（`bounds`、`orientation`、`state`、`isSeparating`）折成 `segments` 与 `posture`。三折叠有两条 `FoldingFeature`。
- 尺寸类：`WindowSizeClass`（compact / medium / expanded）只做日志；布局态由同一套规则算，避免两套阈值打架。
- 合上时窗口在外屏：没有 `FoldingFeature`、窗口变窄，`hasOuter` 由上一次开合记住。
- 世界层：`WebView` 常驻，`onConfigurationChanged` 不重建（Manifest 里 `configChanges` 声明 `screenSize|smallestScreenSize|screenLayout|orientation`）。

### 7.4 iOS 折叠 API

- 首要原则同上：几何驱动状态，不读机型。`StageLayout.fallback(size:)` 就是同一套估法（600 / 0.8 / 1100 / 1.3）。
- iPhone Duo 是否暴露折痕区域、半开状态，要等 iOS 27 SDK 文档确认。确认前 `hover` 在 iOS 上视为不支持，`outer` 视为 `phone`。
- Pencil：PencilKit 的画布只放在日记页，世界不接受笔迹（避免误触）。

### 7.5 折叠屏测试矩阵

| 设备 | 状态 | 必测项 |
|---|---|---|
| 普通直板机（鸿蒙 / 安卓 / iPhone） | 竖屏 | `phone` 完整流程；横屏变 `spread`，抽屉停靠成左页 |
| Pura X Max / Mate X 系列（阔折叠） | 外屏 | `outer`：今日页可读；下一站可点；抽屉半开放得下标题与一行 |
| Pura X Max / Mate X 系列 | 展开横持 | `spread`：跨页左右联动；书脊不压 tile；开合接续到同一天 |
| Pura X Max / Mate X 系列 | 展开竖持 | `phone`（单页放大）：抽屉贴底、世界不被压扁 |
| Pura X Max / Mate X 系列 | 悬停 | `hover`：上半屏世界不跟随；下半屏键盘可输入日记 |
| Mate XT（三折叠） | 全开 | `triple`：左页内容、中页世界、右页弹层；两条折痕都不压可点元素 |

## 8. 微缩世界渲染方案（v0.3：风格化 3D CG）

### 8.1 引擎选择

| 候选 | 鸿蒙 | iOS | 语言 | 判断 |
|---|---|---|---|---|
| **Cocos Creator 3.x** | 官方支持 HarmonyOS NEXT（3.8.6+），渲染走 XComponent | 成熟 | TypeScript | **首选**：与 ArkTS 同源，运行时轻，PBR / 自定义着色、后处理管线都有；CG 质感靠自定义卡通 / 绘画着色器 |
| 团结引擎（Unity 中国版） | OpenHarmony 官方支持，UAAL 已支持 | UaaL 成熟 | C# | 备选：卡通渲染与后处理的现成资产更多，若 Cocos 的画面做不到位就换它 |
| Godot | 只有社区移植 | 成熟 | GDScript / C# | 不采用 |

**2026-09-30 现状（见第 13 节）**：初始框架的世界层先用 **three.js** 做渲染后端——写成 TypeScript、只走桥接消息、在浏览器与 WebView 里都能跑，也能在这个仓库里验证；鸿蒙 `Web` 组件 / iOS `WKWebView` 直接嵌入。Cocos 是 S16 过关后的升级路线，换后端时桥接消息不变。

### 8.2 CG 质感怎么做（不再像素化）

- **相机**：轻透视（视场角约 20°），俯仰约 30° / 90° 两档，方位四档；档位切换用缓动。
- **着色**：卡通 / 绘画式 ramp 着色（两到三阶明暗 + 柔和过渡）+ **轮廓光**（菲涅尔项，角色与地标的亮边），环境光遮蔽（SSAO 或烘焙到顶点色），软阴影（PCF）。不描边。参照《潜水员戴夫》新画风。
- **材质**：积木共用一张小图集（手绘纹理 + 微噪点），颜色为材质参数（换主题只换参数）；倒角用法线或模型自带。
- **光照**：一盏方向光 + 天光；日夜四档切换光色与影子方向；夜里灯窗用自发光 + bloom。
- **后期**：移轴景深（上下带模糊）、暗角、电影感分级（LUT：高光偏暖、阴影偏蓝、对比略高）、轻微胶片颗粒、bloom、粒子（红叶 / 海鸟 / 雪）。按机型分档：高（全开）、中（关 SSAO、bloom）、低（只留暗角与分级）。
- **角色**：一个卡通基础模型 + 骨骼；发型 / 帽子 / 上衣 / 下装 / 鞋 / 配件为独立网格，材质色参数化；动画：走、跑、待机、打卡、坐车。
- **体素与积木**：底板的静态积木合并成少量网格（greedy meshing），倒角在合并后由法线处理；装饰件与用户改过的建筑走实例化；同屏三角形预算 30 万。
- **性能预算**：中端机 60 fps（中档后期），Pura X Max 内屏 60 fps（高档后期）；切换底板 ≤ 500 ms。

### 8.3 嵌入原生页面

- **鸿蒙**：Cocos 导出的 OpenHarmony 工程本身就是 ArkTS 应用，世界画面在一个 XComponent 里；原生页面（书架、悬浮的行程面板、日记、导出）围绕它加，世界铺满整屏，面板悬浮其上（D19）。
- **iOS**：Cocos 集成进已有 Xcode 工程，世界视图作为 UIView 通过 `UIViewRepresentable` 铺满，SwiftUI 面板悬浮其上。
- **桥接**：原生与引擎之间只传 JSON 消息，两端消息一致。原生 → 引擎：加载底板、跳转站点、播放 / 暂停、打卡封顶、进入 / 退出搭建模式、视角档位、后期档位、布局状态（`phone` / `outer` / `spread` / `hover`）与尺寸变化。引擎 → 原生：小人到站、点击建筑、搭建结果（Build JSON）、截图完成。
- **生命周期**：引擎实例常驻，不随页面销毁；切到书架时暂停渲染而不是卸载。

### 8.4 折叠开合时

- 尺寸变化只改渲染目标与相机，世界数据不动；200 ms 内画出新尺寸第一帧。
- 折痕在世界上只是一道光影；悬浮面板由原生布局停靠在折痕两侧。

### 8.5 保留的退路

- Cocos 的卡通着色 / 后处理做不到「精致」（S16 不过）→ 换团结引擎 UAAL，桥接协议不变。
- 引擎嵌入在折叠切换时表现差（S15 不过）→ 世界页改为引擎接管的全屏页，面板由引擎内 UI 画。
- 角色 3D 化的成本失控 → 退回「CG 世界 + 面向相机的高分辨率卡通精灵」（HD-2D 的做法），世界层不变。

## 11. 备选路线与放弃条件

**什么时候改走 Flutter + Flame：** 团队只有一个开发，且这个人有 Flutter 经验、没有 ArkTS 和 Swift 经验。此时一套代码的收益压过平台整合的损失。代价要认：折叠悬停、折痕、实况窗、Pencil 都要自己写 channel；鸿蒙分支的版本要盯；iPhone Duo 首发的新 API 要等。

**什么时候上 Rust 共享核心：** 领域核心超过预期（例如加了复杂的自动排程），两端各写一遍的维护成本明显超过绑定层成本，且团队有人能维护 Rust 工具链。

**什么时候把世界层从 Cocos 换成团结引擎：** Cocos 嵌入原生在任一端跑不通，或体素规模在 Cocos 里达不到性能预算。桥接协议与资源格式不变，换的只是引擎工程。

**什么时候退回像素：** 如果 S16 证明 CG 质感在预算内做不到「精致」，退回 04 文档的「现代像素」路线（同一套积木世界加像素化后处理，角色用高分辨率精灵），地图流水线与世界层代码不变。

**不会改的：** 契约优先、黄金用例、素材单一来源。无论 UI 层怎么换，这三样都留着。

## 13. 初始框架（2026-09-30）

> 仓库主人：这个风格好一点，按照这个风格先搭一版初始的框架，这个视觉肯定后续还要细化的。把关键旅程和页面做出来。

代码在 `app/`，说明在 `app/README.md`。这版做到的：

- **契约先行**：`shared/spec` 的 TS 类型 + JSON Schema（0.2）是唯一事实；`migrate.ts` 把示例数据从 0.1 迁上来；`bridge.ts` 定义原生 ↔ 世界层的全部消息。
- **共享算法有黄金用例**：站点按名字锚定地标 → 路网 BFS 连成路径；时长解析与时间线推算；日记与封面由种子确定性生成。8 个测试全过（七天全部能铺到底板、路径连续、到站索引递增、奈良一日往返的住处标记为跨城）。
- **世界层引擎无关**：`shared/world/world.ts` 只暴露桥接消息；第一版后端 three.js（底板实例化、倒角积木地标、团状树冠、软阴影、雾、渐变天空、三套色调；小人与 Blender 关键视觉同一份设计，脸是贴图贴花；相机跟随 / 全景、30° / 90°、四方位、三级缩放；信息层标牌带避让；播放器到站停顿、乘车段加速）。
- **关键旅程与页面**（网页参考应用）：书架 → 新建旅程（封面实时预览）→ 扉页（翻开动画、序言、世界设定）→ 某一天（世界铺满整屏 + 悬浮的翻页 / 下一站 / 行程面板 / 捏人 / 控制；增删改序、跨天移动、插交通；点建筑加入行程；站点详情打卡）→ 封底（统计、日记、导出长图、合上书）；折叠屏三种布局态；设置。
- **原生壳骨架**：`harmony/`（ArkTS：Ability、五个页面、Web 组件嵌入、`registerJavaScriptProxy` 桥接、折叠态）与 `ios/`（SwiftUI：五个视图、WKWebView 嵌入、`WKScriptMessageHandler` 桥接、布局态）。只是骨架，此环境不编译；页面与网页版一一对应。
- **验证方式**：`npm run check`（tsc + 黄金用例 + 构建）；无头 Chromium 把所有页面与旅程走了一遍（含导出长图），无报错。

与第 1 节结论的差异只有一条：世界层的第一个后端是 three.js 而不是 Cocos（原因见 8.1 节的现状说明），S16 的评审对象变成「three.js 版 vs Cocos 版 vs Blender 关键视觉」。

### 13.4 第九轮：屏幕形态、鸿蒙与安卓、公用的组件（2026-10-08 – 10-09）

> 仓库主人：「除了苹果的版本，这次升华完之后统一继续做鸿蒙的版本。还有安卓的版本。可以公用的组件要公用。」「然后要考虑到折叠屏前后的适配，还有普通直板机的适配，阔折叠的适配，三折叠的适配。」

判断见讨论记录 D90–D93。技术上的做法：

| 模块 | 文件 | 做法 |
|---|---|---|
| 屏幕形态 | `shared/spec/layout.ts`、`layout.golden.json`（22 条）、`web/src/shape.ts`、各端移植 | 第 7 节：五个布局态、按页停靠、四边留白；网页 `?fold=closed\|2\|3\|half` 模拟 |
| 公用的领域核心 | `shared/core.ts`（带测试）、`web/src/embed.ts`、`bridge.ts` 的 `core-call` / `core-result` | 原生按名字调一个纯函数，参数与结果都是 JSON；新壳不再移植算法——四端结果天然一致，黄金用例只需在 TypeScript 这一份上跑 |
| 消息频道 | `shared/spec/channels.ts` | 每种消息是「状态」（按频道留最新一条、就绪后按序重放）还是「一次性动作」；少一项类型检查就报错。iOS 的 `WorldChannel` 照它，鸿蒙、安卓读导出的表 |
| 桥接修正 | `shared/world/world.ts`、`bridge.ts` | 底板建好后原来也发 `ready`，而原生收到 `ready` 会重放全部状态（含 `show-day`）——会无限重载。改成底板建好发 `plate-loaded`；`ready` 只在页面加载完发一次 |
| 导出 | `tools/export-shared.ts`（`npm run export:shared` / `sync:shells`） | 消息表 JSON、令牌、桥接表、布局阈值与用例 → 鸿蒙 `rawfile/shared/`、安卓 `assets/shared/`；两端的常量源文件 `gen/Shared.ets`、`gen/Shared.kt`；应用名与权限说明的系统资源；`--world` 把 `web/dist` 拷进两端（不进版本库） |
| 鸿蒙 | `app/harmony/` | 第 5 节开头的说明；ArkWeb 常驻、虚拟 https 源、`harmonyBridge`；`LayoutState.ets` 读 `getFoldStatus` / `getCurrentFoldCreaseRegion` |
| 安卓 | `app/android/` | 第 6.1 节；`WebViewAssetLoader`、`androidBridge`、WindowManager 的 `FoldingFeature` |
| 长图（D96） | `web/src/export.ts`、`web/src/embed.ts`、`bridge.ts` 的 `export-long-image` / `long-image-progress` / `long-image` | 网页那一份排版给四端用：嵌入页借常驻的世界层逐天建底板、拍一张、拼成 PNG 回 data URL；三端日记页都改用它（iOS 拿不到时退回原生文字版）。时限按天数给，世界层重载时作废 |
| 照片小卡（D99） | `web/src/case-cards.ts`、`embed.ts` 的 `make-card` / `card-made`、安卓 `util/CaseCards.kt`、鸿蒙 `util/Photos.ets` | 抠图一份（网页的本机漫延法）：两端只管选照片、缩图、存卡；iOS 先 Vision、不行再走它 |
| 三端契约（D97） | `shared/spec/shell-contract.test.ts`、`tools/export-shared.ts --check`（`npm run check:shared`） | 扫各壳源码里写死的消息种类、核心函数名、文案键，对照桥接、`core.ts`、消息表；要回话的请求必须接回话；iOS 手写频道与 `channels.ts` 一致。生成文件过期也算失败——原生壳在这里编译不了，这是能做到的最早拦截 |

为什么领域核心走桥接而不是各写一份：iOS 那份 Swift 移植（PRNG、日记、时间线……）当初要逐字对齐 TypeScript，靠黄金用例一项项追；再加两端就是三份要追。世界层本来就常驻在每个壳里，核心函数又都是纯函数、只吃 JSON，借它跑是零成本的复用。代价是这些调用是异步的（一次几毫秒），而且世界层没加载好之前调不了——所以原生只在「世界就绪后」用它（首屏的旅程状态等它回来再画卡片），离线也照样能用（核心不联网）。iOS 已有的 Swift 版保留。

没跟上的：鸿蒙、安卓都没编译过（这个环境没有 DevEco 与 Android SDK）；各自的 README 列了拿不准的接口。付费（AppGallery 内购、Play Billing）、同步、语音识别在两端都还是 TODO。
