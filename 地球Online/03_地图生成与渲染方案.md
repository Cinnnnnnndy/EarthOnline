## 1. 先说结论

- **没有现成的开源引擎能把 OpenStreetMap 直接渲染成像素游戏地图。** 调研到的最接近的讨论（OSM 社区「用 libosmium 生成某地的像素 tilemap」）结论也是「自己拼」。
- **但每一段都有成熟开源件**：取地图数据（OSM + Overpass / osmium / tilemaker）、把数据栅格化成分类网格、按规则自动铺 tile（LDtk 的 auto-layer 规则体系）、输出通用 tilemap 格式（Tiled / LDtk JSON）、渲染（自研 Canvas / SpriteKit，或 Phaser / PixiJS / Cocos）。
- **建议把生成放在服务端**，按目的地区域生成一次、缓存、下发 tilemap JSON；客户端只负责渲染和小人。这样「适配大量目的地」变成服务端跑批与规则调优，不是手工作业，也不给两端客户端增加逻辑。
- **「大量适配」的工作量落在两处**：一是每个地形主题（biome）一套积木模块库、一套地面铺法规则（LDtk 编辑器里可视化配置）和几套建筑模板；二是分类规则（什么 OSM 要素算道路、算绿地）的调优。两者都是数据，不是代码。
- v0.2 之后世界是 3D 的：地面仍按二维规则铺，建筑按 OSM 轮廓与层数**堆**成积木块，站点换成类别模板。同一条流水线，多一个高度维度。

## 2. 问题拆开看：两件事，不是一件

「把地图渲染成对应的样子」其实是两个独立问题：

| 问题 | 输入 | 输出 | 谁解决 |
|---|---|---|---|
| **几何**：这个城市的路、河、公园、建筑在哪 | 真实地图数据 | 分类网格（IntGrid：每格是道路 / 水 / 绿地 / 建筑…） | OSM 数据 + 栅格化脚本 |
| **画法**：这些格子用哪块像素 tile 画才好看 | 分类网格 + 地形主题 | 铺好 tile 的地图 | 自动铺 tile 规则引擎（autotiling） |

游戏行业早就把第二个问题解决得很好（LDtk、Tiled 的 Wang/Terrain、Godot 的 Terrain 都是这一类），第一个问题 GIS 行业解决得很好（OSM 生态）。缺的只是中间那一小段把两者接起来的脚本。

## 3. 流水线：真实地图 → 像素世界

```
目的地 / 某一天的站点
   │  取 bbox（站点外扩一圈）
   ▼
① 取数据  OSM（Overpass API 在线；或离线 PBF 用 osmium / tilemaker / GeoDesk 查询）
   │  要素：道路(highway 分级) 水体 绿地/公园 建筑轮廓 铁路 海岸线 广场 沙滩 地标 POI
   ▼
② 栅格化  bbox 切成 64×64 网格 → 每格投票分类 → IntGrid
   │  规则：道路细化为 1 格宽并保证连通；建筑合并成块；清孤点；水体平滑
   ▼
③ 自动铺积木模块  IntGrid + 地形主题(biome)
   │  地面层：规则引擎按 3×3 邻域模式匹配选地面 / 道路 / 水面 / 岸边模块（LDtk 导出的规则 JSON）
   │  建筑层：按 OSM 轮廓与层数（building:levels / height，缺失时按类别默认）堆成积木块，屋顶按模板
   │  装饰层：树、路灯、长椅按规则与种子撒
   ▼
④ 放站点与路径  站点吸附到最近道路格 → 站点所在建筑块换成类别模板（Build）→ A* 在道路格上寻路
   │
   ▼
底板 JSON（地面模块网格 + 高度图 + 建筑块列表 + 实体层）→ 缓存 → 下发客户端，由引擎世界层渲染
```

**尺度约定（第二轮修订）**：底板是**城市尺度**，一格约 100–300 米，按当天站点外接框自适应，64 × 64 格封顶。取的是骨架而不是楼：主干道（`highway=trunk/primary/secondary`）、铁路与地铁（`railway=rail/subway`，地铁画成虚线）、河流海岸（`waterway`、`natural=water/coastline`）、大型绿地（`leisure=park`、`landuse=forest`）、山（`natural=peak`、林地，可选接高程数据）、建筑密度（每格建筑数 → 肌理里小砖的疏密）、地标 POI。单体建筑轮廓只在站点处取用，用来定地标模板的底座。站点之间的空白段按比例压缩，保持相对方位。示意见 `示意图/城市尺度_京都一日.png`。

每一步的要点：

**① 取数据。** 原型阶段用 Overpass API 在线取 bbox 就够；上线后自己维护 OSM 切片（PBF 提取 + osmium / tilemaker 预处理，或 Protomaps 的 PMTiles 全球离线切片），避免依赖公共 Overpass 的速率限制。

**② 栅格化。** 这是「像不像那个城市」的关键。经验规则：
- 网格分辨率随 bbox 自适应：老城区一天走 3 公里，一格约 50 米；跨城日拆成多个区域（产品构想 5.2 已约定）。
- 道路只保留能走的主干与步行道，其余丢弃，否则 64×64 里全是路。
- 建筑不逐栋画，按街区合并成「建筑块」，站点所在的块换成具体建筑 tile。
- 分类冲突时优先级：站点 > 水 > 道路 > 铁路 > 绿地 > 建筑 > 空地。

**③ 自动铺积木模块。** 城市尺度下街区不堆楼：普通街区格铺浅色底板，按密度撒零星小砖（一格最多一块）；山格按高度堆 1–3 层绿到灰的积木；站点格换成放大到 2–4 格的地标模板（寺庙、鸟居、城、车站、町屋……按类别与主题选）。地面层沿用 LDtk 的 auto-layer 规则模型：每条规则是一个 3×3（或更大）的模式，匹配 IntGrid 邻域后决定放哪块地面模块，可带随机权重。设计师在 LDtk 里用「规则助手」画一遍标准布局（直道、拐角、丁字、十字、岸边、林缘），LDtk 自动生成全部方向的规则；导出 JSON 后，服务端用同一套规则逐格匹配。建筑层不用规则而用「堆」：每个建筑格按层数堆基础砖，顶层按模板放屋顶（平顶 / 坡顶 / 塔顶），层数来自 OSM 的 `building:levels` 或 `height`，缺失时按类别默认（民居 2 层、商业 4 层、地标按模板）。**地面规则 + 模块库 + 建筑模板是每个 biome 的核心资产**，配一套大约 3–4 天。

**④ 放站点与路径。** 站点坐标 → 网格 → 吸附到最近道路格；同格冲突按顺序向外螺旋找空位；站点所在的建筑块换成类别模板生成的 Build（底座取 OSM 轮廓，模板按类别与种子选）；A* 四方向在道路格上走，启发式与平局规则写死（一致性要求见技术选型 4.3）。

产出物是一份底板 JSON：地面模块 id 网格、高度图、建筑块列表（位置、层数、屋顶、是否站点）、实体层（站点、住宿、NPC、路径点）。世界层引擎按它实例化积木；用户改过的 Build 单独存，覆盖对应建筑块。

## 4. 可用的开源件清单

| 类别 | 名称 | 许可证 | 用途 | 说明 |
|---|---|---|---|---|
| 地图数据 | OpenStreetMap | ODbL 1.0 | 全球道路、水体、建筑、POI | 必须署名；覆盖率因地区而异 |
| 数据查询 | Overpass API | 服务；公共实例有限流 | 按 bbox 取要素 | 原型用公共实例，上线自建或改离线 |
| 数据处理 | osmium / libosmium | Boost | PBF 读取与过滤 | 离线切片预处理 |
| 数据处理 | tilemaker | 宽松许可（以项目页为准） | OSM PBF → 矢量切片 | 自己维护切片时用 |
| 数据查询 | GeoDesk | 以项目页为准 | 对 OSM 要素做空间查询的库 | OSM 社区在「像素 tilemap」讨论里点名的方案 |
| 离线切片 | Protomaps / PMTiles | BSD | 单文件全球矢量切片 | 离线包与自托管的低成本方案 |
| 切片规范 | OpenMapTiles | BSD + CC-BY | 矢量切片 schema 与样式 | 若走「像素化真实地图」路线 |
| 规则编辑 | LDtk | MIT | IntGrid、auto-layer 规则、JSON 导出 | 设计师配置铺 tile 规则的主工具 |
| 地图格式 | Tiled（libtiled） | 编辑器 GPL，库 BSD | TMX / JSON 地图格式；手工修饰 | 作为交换格式；Cocos、Phaser、Godot 都能读 |
| 像素绘制 | Aseprite | 源码开放，二进制付费 | 画纹理与精灵 | 单一素材来源（技术选型 4.6） |
| 体素建模 | Goxel | GPL（工具，不影响产物） | 画积木与模板 | 开源；导出 glTF / OBJ |
| 体素建模 | MagicaVoxel | 免费，非开源 | 同上 | 更顺手，格式需转 glTF |
| 渲染（Web） | Phaser | MIT | 2D 游戏框架，内置 Tiled 地图与 tilemap 支持 | 若两端共用一个 WebView 渲染器 |
| 渲染（Web） | PixiJS | MIT | 2D WebGL 渲染器 | 比 Phaser 更底层，配 tilemap 插件 |
| 渲染（引擎） | Cocos Creator 3.x | 免费，自有许可 | 3D 场景、实例化、后处理；鸿蒙 NEXT 与 iOS 官方支持 | **v0.2 起的世界层首选**，见技术选型第 8 节 |
| 渲染（引擎） | Godot | MIT | TileMap + Terrain 自动铺 tile | 鸿蒙侧只有社区移植（无官方支持），不建议作为主路线 |
| 真实地图渲染 | MapLibre GL JS / Native | BSD | 矢量地图自定义样式 | 「像素化真实地图」路线；鸿蒙无原生版，只能走 ArkWeb |

## 5. 渲染端怎么选

v0.2 之后世界是带角度的 3D 积木，渲染端的选择已在技术选型第 8 节定为「游戏引擎世界层，两端共用一份代码」。这里只记录与地图流水线相关的取舍：

| 方案 | 两端共用 | 3D 与后处理 | 折叠屏 | 结论 |
|---|---|---|---|---|
| **Cocos Creator 3.x 嵌入原生页面** | 是，一份 TS | 现成 | 引擎视图随原生布局改尺寸 | **主路线** |
| 团结引擎 UAAL | 是，一份 C# | 现成，更强 | 同上 | 备选 |
| 自研 2D（ArkUI Canvas + SpriteKit） | 否 | 无 3D，无法做带角度视角与积木堆叠 | 好 | v0.1 的方案，仅作为「退回 2D」时的路线 |
| Three.js 跑在 WebView | 是，一份 JS | 现成 | WebView 尺寸变化要小心 | 兜底 |
| Godot | 理论上是 | 现成 | 未知 | 不采用，鸿蒙侧只有社区移植 |

关键不变：**几何生成在服务端，渲染端只做「按底板 JSON 实例化积木 + 小人动画 + 搭建编辑」。** 底板 JSON 的格式是契约，换引擎不换格式。

## 6. 两种风格路线：游戏世界 vs 像素化真实地图

| | A. 积木微缩世界（IntGrid + 自动铺积木模块，带角度的 3D） | B. 像素化真实地图（MapLibre 自定义样式） |
|---|---|---|
| 做法 | 第 3 节流水线 | 用 OSM 矢量切片 + 平涂色样式 + 像素纹理填充，低分辨率渲染后最近邻放大 |
| 观感 | 像摆在桌上的一座积木小城：抽象、有建筑、有 NPC、能走、能搭 | 像给真实地图加了像素滤镜：精确、信息密、没有「世界感」 |
| 小人能走吗 | 能，路径在道路格上 | 能沿真实路网走，但没有格子语义 |
| 任意目的地 | 能，但依赖 OSM 覆盖率；稀疏地区退化为抽象布局 | 能，全球一致 |
| 折叠屏跨页 | 天然适合「一页放下整天」 | 就是一张地图 |
| 鸿蒙可行性 | 引擎世界层，官方支持 | 只能 ArkWeb 里跑 MapLibre GL JS |
| 适合做什么 | **主视图**：探索视图 | 备选的「真实地图页」；或 P0 之前 1 周内出的快速原型 |

推荐 **A 为主**，产品的差异点（世界、NPC、走站、翻页）都建立在 A 上。B 的价值是快：如果要在开工前给别人看一眼「像素地图长什么样」，用 MapLibre 一天能出效果，但不要把它当成最终路线。

## 7. 规模、缓存、离线与许可证

- **缓存键**：`(bbox 量化后, 网格分辨率, biome, tileset 版本, 规则版本)`。同一城市的热门区域会被大量复用；一张 64×64 的生成目标 < 1 秒。
- **离线**：出发前把整趟旅程的 tilemap JSON 与 tileset 打进本地；旅行中不联网也能看。tilemap JSON 一张几十 KB，一趟旅程几百 KB 以内。
- **覆盖率兜底**：OSM 在部分地区数据稀疏。栅格化后若道路格占比低于阈值，退化为「抽象布局」：站点按相对方位放置，道路由生成器补一条主路连起来。这条兜底逻辑 P0 就要有，否则第一次遇到数据空白就翻车。
- **许可证**：OSM 数据 ODbL 要求署名（App 内「关于」页与导出的日记页脚写「© OpenStreetMap contributors」）；用 OSM 数据派生的 tilemap 属于「产生的作品」，按 ODbL 指引处理，上线前请法务过一遍。LDtk、Phaser、PixiJS、MapLibre 都是 MIT / BSD，无传染性；Tiled 编辑器是 GPL，但我们只用它的格式和 BSD 的库。
- **成本**：服务端跑批是 CPU 任务，不用 GPU；一次性预生成全球热门城市的核心区域是可选优化，不是前提。

## 8. 对前两份文档的修订

- 产品构想 5.2「空间组织」原来写的是「按经纬度归一化到网格 + 规则避让」。这仍然是**兜底路线**（OSM 数据稀疏时启用）；主路线改为本方案的 OSM → IntGrid → 自动铺 tile。
- 产品构想 5.3「世界生成」拆成两半：**风格**（biome、色板、tileset、文案）仍由规则表 + 种子生成；**几何**（路、河、建筑块）由本方案生成。两者在 `WorldSpec` 里分开存：`style` 与 `mapRef`。
- 技术选型第 3 节的共享层新增 `mapgen/`：服务端生成器、分类规则、biome 的 auto-layer 规则 JSON、tilemap 输出格式定义。黄金用例增加一类：同一 bbox + 同一规则版本 → 同一 IntGrid → 同一 tilemap，逐字节一致。
- 技术选型第 9 节的节奏：生成器在第 1–2 周随契约一起起步，用东京 / 京都 / 冲绳三个真实 bbox 跑通，作为黄金用例的地图来源。
- v0.2 修订：产品构想 5.2 的世界改为 3D 积木、5.6 新增搭建模式；本方案第 3 节第 ③④ 步与第 5 节随之改；`WorldSpec.mapRef` 指向的「底板 JSON」多了高度图与建筑块列表；用户改过的 Build 单独存（产品构想 8.2）。

## 9. 要补的 spike

| # | 验证什么 | 通过标准 |
|---|---|---|
| S9 | OSM → IntGrid → 自动铺积木模块，三个真实 bbox（京都核心区、东京山手线内、冲绳那霸），城市尺度 1 格 ≈ 250 m | 以 26.6° 视角渲染后，不看图例也能认出是哪座城（靠山、河、路网、铁路的骨架）；主干道连通；地标放大后不互相遮挡 |
| S10 | LDtk 地面规则导出 JSON 后在服务端复现 | 服务端铺出的地面模块与 LDtk 编辑器内预览逐格一致 |
| S11 | 覆盖率兜底 | 挑一个 OSM 数据稀疏的 bbox，退化布局可用且不报错 |
| S12 | 底板 JSON 在世界层渲染 | 同一份 Cocos 工程在鸿蒙与 iOS 上画出同一座城；换一个 biome 的模块库不改代码 |
| S13 | 站点模板 → Build | 五类站点各出两套模板，底座取 OSM 轮廓后仍然好看；用户改一块砖后落库与还原正确 |
